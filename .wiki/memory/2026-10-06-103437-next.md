# Pipeline philosophy switched to automated comparison tables; regrouped into three sequential specs (PR #19–#21 merged)

Ahead of a PDF report due the next day, the user asked whether the 입찰메이트 (BidMate) RAG pipeline covered nine report items: parsing, chunking comparison, BM25 vs Kiwi BM25, embedding×hybrid comparison, golden dataset, judge set, DB maintenance, chat frontend with sources, and reranker comparison. Only parsing, K0/K1 BM25, the golden process and manual maintenance were documented. The user then changed the project philosophy: pipelines run every variant and a person picks from comparison tables. This meant rewriting the plan documents. The user chose 13 embedding models and 8 local rerankers, and the work was regrouped into three larger specs run in order. PRs #19, #20 and #21 were then merged (round 5, 0 remaining P2).

## Decisions

- Switch to an automated-pipeline philosophy: the pipeline runs every variant on frozen question sets and writes one comparison table, and the person only picks from the tables. AI review replaces human gold approval. The plan documents themselves are rewritten. — The user said people can compare numbers and trade-offs easily when they are laid out, so this does not hurt human decision-making. (rejected: Manual per-step CLI comparisons, gold approval by a different named person, and an owner-filled decided_by/rationale)
- Embedding comparison of 13 user-selected models, each scored dense-only and as a hybrid with Kiwi BM25. Local: BAAI/bge-m3, nlpai-lab/KURE-v1, dragonkue/BGE-m3-ko, Qwen/Qwen3-Embedding-0.6B, Snowflake/snowflake-arctic-embed-l-v2.0, dragonkue/snowflake-arctic-embed-l-v2.0-ko, ibm-granite/granite-embedding-278m-multilingual, google/embeddinggemma-300m, jinaai/jina-embeddings-v3, Alibaba-NLP/gte-multilingual-base. API: OpenAI text-embedding-3-large @1536 (current serving), text-embedding-3-small, Google gemini-embedding-001. — The user wanted as many candidates as fit the project, then a multi-select and a full comparison.
- Reranker comparison of 8 local models, each run in two modes (whole list, and below the BM25 head): bge-reranker-v2-m3, dragonkue/bge-reranker-v2-m3-ko, bge-reranker-v2-gemma, bge-reranker-v2-minicpm-layerwise, Qwen3-Reranker-0.6B, mxbai-rerank-base-v2, mxbai-rerank-large-v2, gte-multilingual-reranker-base. — The user wanted as many candidates as fit the project, then a multi-select and a full comparison. (rejected: API rerankers (API 리랭커는 안 고른다))
- Build the LLM-judge golden set by synthesizing negatives from known-correct answers.
- DB and vector maintenance runs as one button or command for the whole sequence, with no schedule. (rejected: Scheduled automation)
- The chat frontend becomes multi-turn and streaming, with sentence-level citations and the side evidence pane.
- The work is regrouped into three large specs, started in order, each from main after the previous one is merged. (1) All retrieval comparisons: plan rewrite, matrix runner, 실험 비교 screen, and the chunking, K0/K1, golden-count, embedding and reranker tables. (2) Judge golden set plus one-command maintenance. (3) Conversational answer screen. — The user asked for specs that finish when started in order from the top, each with a large scope. Spec 2 needs spec 1's runner for its regression step. Spec 3 should be built on the retrieval setup activated from spec 1. (rejected: An earlier split into six specs (automated-comparison-pipeline first, the rest in parallel))

## Facts

- Project 입찰메이트 (BidMate): an internal RAG assistant over 100 Korean RFPs (96 HWP, 4 PDF). It uses a Next.js frontend, a FastAPI backend, and PostgreSQL 18.6 with pgvector. (unverified)
- HWP is parsed with pyhwp `hwp5proc` into structured XML, and PDF with PyMuPDF as text blocks plus tables. 94/96 HWP files parsed, and the 2 failures are quarantined. There are 98 active sources. (unverified)
- Parsing fidelity check: a Hancom Viewer print to PDF is compared both ways against the extraction, and each document is marked auto_verified or auto_flagged. Text inside images is read by PaddleOCR-VL, with a Gemini Flash-Lite fallback capped at $0.50. (unverified)
- Active chunks: 18,983 in keyword index 29f261abafeb1f8c at the 2026-10-04 cutover. There are 178,049 chunk rows across all index versions. The serving chunker is structural-5: target 700 tokens, hard limit 800. (unverified)
- Chunk profiles structural, fixed-256-32, fixed-512-64 and fixed-800-96 exist, but only structural was ever measured. A free comparison: `build-keyword --profile fixed-512-64 --no-activate`, then `evaluate-retrieval --runs K1 --index <version>`. (unverified)
- K0 (standard BM25) vs K1 (Kiwi BM25): nDCG@5 0.6696 vs 0.9500, MRR 0.6647 vs 0.9612, correct claims 169/250 vs 224/250, fully complete questions 28/50 vs 44/50. (unverified)
- Hybrid with 3-large@1536 scored nDCG@5 0.7696 vs K1's 0.8168. The tuned keyword_first fusion now serving scored 0.9405 and found 32 of 33 needle targets in the top 5. (unverified)
- bge-reranker-v2-m3 failed its gate (nDCG@5 0.8948 vs 0.9405 hybrid) and is not served. (unverified)
- Gold sets: 50 approved development rows (Phase 4 pilot) vs 55 frozen development questions in later measurements. Also a 14-row sealed test set, a 33-question needle set, and 181 candidates in the pilot archive. (unverified)
- The judge reference is 750 items from development run A-9ef59b566d64, split into 373 calibration and 377 held-out items, with only 13 negatives held out. Jev was judged not replaceable for Luna (6 false accepts vs a limit of 5). (unverified)
- Gold labels are exact source spans, not chunk IDs. `gold generate`, `gold repin` and `gold status` exist. (unverified)
- Maintenance commands: ingest, build-keyword, backup, restore-check and activate-run. All are manual. (unverified)
- The 질문하기 page has per-claim citation chips and a side evidence pane, but each question is an independent request with no streaming. (unverified)
- Serving startup refuses any embedding other than text-embedding-3-large @1536. Spec 1 adds activation of any table row, embedding rows included (local or API). (unverified)
- Spec 1 keeps the serving limits fixed in every row: 50 candidates per channel, 10 evidence units, and keyword_first fusion keeping the BM25 top 6. (unverified)
- Hardware: one RTX 3080 with 10 GB. The OpenAI ledger has about $7.86 left under its $10 cap. (unverified)
- jina-embeddings-v3 is non-commercial and embeddinggemma-300m is under Gemma terms; both are labelled research-only. (unverified)

## Preferences

- Automated pipelines over manual steps. The person compares easily readable numbers and trade-offs, then decides.
- For model choices, wants as many candidates as possible fitted to the project's nature, then picks several to compare as a whole.
- Wants specs with a large scope that complete when started in order from the top.
- Comparison screens (embeddings, rerankers) must be in the frontend.
