# Review of the user's EVALUATION/VALIDATION/DATASETS/frontend defect analysis, with all fixes split into five grouped specs (PR #28 merged)

The user shared a detailed defect analysis of their areas (evaluation, validation, dataset generation, frontend) at commit 1766522 and asked for it to be checked. The assistant said every code-level finding still holds on main 0722a69, narrowed the reach of the scoring-inflation finding, and flagged the reranker NameError as possibly the highest-impact bug. The user agreed to apply everything and asked for several grouped specs rather than one. The assistant produced five specs and proposed three design choices that the user did not answer. The final result line reports PR #28 merged (round 2, 0 remaining P2).

## Decisions

- Apply all findings from the analysis, including the section 4 gaps.
- Split the work into several specs grouped by area instead of a single spec. The assistant made five: specs 1–4 are independent and can run in parallel, and spec 5 (fresh evaluation) waits for specs 1 and 4 to merge. — Spec 5 would otherwise measure the old, too-generous scoring. (rejected: a single combined spec)

## Facts

- Evaluation status check compares the answer against every status allowed for the `answerability` category, not the row's own `expected_status`. An `insufficient_evidence` row answered with `clarification_required` passes (status_ok=True, passed=True). src/rfp_assistant/service/answers.py#L548-L559
- This inflates the per-question pass rate and the 부정·모호 질문 처리 gate (release line ≥ 90%). An `answered` reply to an unanswerable question still fails. (unverified)
- A claim is marked supported as soon as any citation link is reviewed `supporting`, unless a separate whole-claim review exists. The judge definition treats `supporting` as 'at least one part' of the claim, and whole-claim support is the separate `answer_claim` item. src/rfp_assistant/service/answers.py#L605-L638, src/rfp_assistant/evaluation/judges.py#L462-L480
- The claim inflation only hits claims that have a 'supporting' link verdict and no `answer_claim` review. Unreviewed links count only when the whole claim appears verbatim in the quote. (unverified)
- Dataset draft pre-check picks single or compare mode from the document count but never checks it against the question type. The rule (2 documents ⇔ `cross_document`) only runs on the finished gold row, after the paid call. src/rfp_assistant/service/drafting.py#L176-L223, src/rfp_assistant/evaluation/evaluation.py#L2338-L2341
- `gold.submit` blocks any submission while any rejected candidate in any dataset, including sealed test, has no recorded cause. The error is 'infer why these candidates were rejected before drafting more: sealed-hidden-r1'. `drafting.lessons()` already excludes `dataset = 'test'`. src/rfp_assistant/evaluation/gold.py#L367-L381, src/rfp_assistant/service/drafting.py#L155-L165
- `validate_answer()` accepts `status="conflicting_evidence"` with empty conflicts, a single alternative, or `next_action=None`. Offline scoring does require `next_action`. src/rfp_assistant/gateway/generation.py#L537-L590
- Fixing the `validate_answer` conflict check changes what gets served, so it needs a new prompt/validation version, and earlier sealed results stay as they are. (unverified)
- `usePoll()` keeps the previous key's data when the fetch for a new key fails, so stale results show under the new target. The judges screen shows no fetch error. web/src/lib/use-poll.ts#L25-L48, web/src/components/verify/judges.tsx#L60-L88
- `/api/ask` generates a fresh UUID as the idempotency key on every call, so a retry after a lost response creates a second request and executor submission. The DB duplicate protection already exists. src/rfp_assistant/service/service.py#L2737-L2746, #L948-L973
- web/src/components/dataset/draft.tsx#L200-L215 has no catch/finally, so a network error leaves `busy=true`. The pattern to reuse is in web/src/app/settings/page.tsx#L39-L49
- `LocalReranker` uses an undefined `device` in `getattr(self.model, "device", device)`. src/rfp_assistant/retrieval/dense.py#L677-L681
- Every `LocalReranker` construction raises NameError, and the line dates from phase 2. (unverified)
- `judges.run()` writes status `stopped`, which the `requests` table does not allow (queued/running/completed/failed/cancelled/interrupted). src/rfp_assistant/evaluation/judges.py#L1009-L1021
- Because the `stopped` write is in a `finally`, a stopped judge run raises before `finalize` and no final report is written. (unverified)
- The time parser treats '오전 12시' as 12:00 instead of 00:00, which affects deadline scoring. src/rfp_assistant/evaluation/evaluation.py#L2022-L2035
- Two verification automation problems are recorded as unfixed in PR #26: the release walkthrough does not pass DB env vars to the child CLI, and the budget-cap browser check waits for the removed name field.
- Dataset generation is limited to 7 answerable types (src/rfp_assistant/service/drafting.py#L30-L43). `gold infer` exists only in the CLI.
- Automated review of valid evidence outside the gold labels is marked not implemented (src/rfp_assistant/evaluation/evaluation.py#L769-L774). Such evidence scores 0, which affects nDCG.
- Judge calibration/held-out split is per item, not per question (src/rfp_assistant/evaluation/judges.py#L208-L226).
- Pilot scores in docs/operations/release-report.md#L56-L84 (dev 50, sealed 14) came from an older prompt and are not current performance.
- Current main was 0722a69 at review time. PR #27, the only merge after 1766522, changed only the verification screen layout and pass lines. (unverified)
- Specs 2 and 3 both touch web/src/components/dataset/draft.tsx, so expect a merge conflict there. (unverified)
- PR #28 was merged: round 2, remaining P2 0.

## Preferences

- Reflect all findings (모두 반영).
- Don't write one spec. Group the work broadly into N specs (명세를 하나로 하지 말고, 크게 묶어서 N개로).

## Open

- Unconfirmed design choice for grading: by default only the row's own `expected_status` passes, and extra accepted statuses must be listed explicitly in gold.
- Unconfirmed design choice for claim support: a claim counts as supported only if it is quoted verbatim from a cited passage or a whole-claim review says so, never from a link verdict alone.
- Unconfirmed design choice for generated 'not in the document' questions: they must prove absence by checking the whole document, not top-k results.
- Check whether the reranker comparison or serving path actually builds `LocalReranker`. If it does, that is the highest-impact bug.
- How often claim-support inflation occurs in real runs was not measured.
- Duplicate question/document-family overlap in private judge data was not measured.
- The PR #26 automation issues were not rechecked in code.
- Spec 5's paid evaluation run must stop and ask the user before spending. Which specs PR #28 covers is not stated.
- No full integration run was done against the operating DB, private source documents, a real GPU or paid models.
