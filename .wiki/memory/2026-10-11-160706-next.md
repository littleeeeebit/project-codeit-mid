# Gap analysis of the eval pipeline against a human-led error-analysis philosophy, and a five-PR review-UI plan (PRs #39–#43 merged)

The evaluation-pipeline owner asked which parts of a talk's philosophy are already applied and which are missing. The philosophy is that a person discovers failure criteria by reading real output, and AI organizes, counts and re-applies them. The owner also asked for the speaker's examples to be translated to this project. The assistant found the saved criteria, the risk-based gates and the distrust of AI judges already in place. Bottom-up annotation of answers, failure-type counting, 'find more cases' and sampling of real traffic were missing. The assistant then proposed five PRs centred on a human-readable review UI, and PRs #39–#43 were all merged; #42 still has 1 P2 left.

## Decisions

- Build the work as five sequential PRs: review-ui-readable, answer-span-annotation, failure-taxonomy-from-notes, similar-case-proposals, traffic-sample-review — Two PRs fix and build out the review screens. Two complete the human-led loop: mark → group into types → count → find more. The last points that loop at real consultant traffic as well as the gold set. (rejected: Separate PRs for risk-based gates and the judge comparison, which already follow the philosophy)
- Every PR requires a Chrome walkthrough, one screen-height at a time, with before/after screenshots, and fixes for whatever the walkthrough shows — The owner made a human-readable UI the top priority, and the assistant's UI findings came only from reading code, not from viewing the screens
- On the 검증 page only the evaluation sections are in scope; 유지보수, 수집 상태, 수정 기록 and 요청 기록 stay out — They are operations screens
- None of the five PRs makes a paid API call; grouping and similar-case search go through the coding agent using files the app writes — It follows the way decision files already work
- AI groups human notes into failure types and proposes more cases; a person accepts, renames, merges or rejects; AI does not invent criteria on its own — The speaker's point is that a person discovers the criteria and AI only applies them (rejected: AI reviewers setting the standard, as in the current operating rule)

## Facts

- Gold-question drafting rejections use fixed codes (`leading_question`, `too_easy`, `evidence_mismatch`). `gold infer` records `cause`/`lesson`/`drafting_rule` for each rejection, `gold submit` refuses new batches while any rejection lacks them, and learned rules feed the next generation prompt (unverified)
- Independent review round 22 of answers from prompt `grounded-answer-3` found omitted obligations and a missing conflict action; `grounded-answer-4` added atomic obligations, completeness checks and asking the purchaser for clarification, and the next run reached 225/246 correct required claims (91.46%) (unverified)
- An owner check in the app (asking about 한영대학교, then asking for the answer "더 쉽게") showed the follow-up dropped the budget, period and contract method, and made students the users of functions the document assigns to no one; both became fixes (unverified)
- Critical claims are labeled `deadline`, `amount`, `mandatory_condition` or `institution`; release requires zero critical misstatements, and scope leakage is a hard check (unverified)
- The design keeps unknown (field verifiably missing), unavailable (ingestion failed) and 'ask a clarifying question' apart instead of using one refusal score (unverified)
- Luna vs Jev judge comparison: both kappas are below 0.25, verdict is not replaceable; a reference with more negatives, especially human-reviewed failures, is needed first; LLM judges only grade a bounded sample (unverified)
- Review surfaces: the 검증 page has 검색 추적 and 추적 비교 (trace viewer) and 할 일 (inbox); the stage-review app shows candidates side by side with evidence, separated claims and validation failures; Langfuse links each answer to its trace (unverified)
- The 검증 menu was regrouped on 2026-10-07 because the owner couldn't tell its sections apart (unverified)
- Review selection is rule-based, not clustering. The blind review sheet holds only uncertain, wrong-value, contested or critical claims. The OCR comparison reads every flagged image plus a seeded sample of 30 passes. Gold excerpts are stratified into `numeric_qualifier`, `late_table`, `repeated_code`, `deadline` (unverified)
- Before these PRs, answer review verdicts came from a fixed set, the 120-question type split was planned in advance, the release report listed failures as prose without counts by type across runs, and `rescore` only re-grades stored outputs mechanically after a scorer fix (unverified)
- Before these PRs, evaluation ran only on the gold set; request records and Langfuse traces of real consultant questions were not sampled. Phase 5 adds a regression row for each accepted correction (unverified)
- Each candidate has roughly 50–55 dev answers (unverified)
- Generation comparison screen issues found from code: internal codes as main labels (question type, `claim_without_evidence 3`, question ID), squeezed answer columns with 3+ candidates, "필수 1 누락" badge separated from its claim, decision panel at the very bottom, and notes only per question rather than per answer span (unverified)
- traffic-sample-review samples real answers from `requests` read-only, replaces member IDs with pseudonyms, and shows why each answer was picked (unverified)
- PRs #39, #40, #41, #42 and #43 were merged after 4, 4, 3, 5 and 6 review rounds; #42 merged with 1 P2 remaining, the others with 0

## Preferences

- The most important thing is a UI that is easy for a person to read ("사람이 보기 편한 ui"); the assistant must actually look at the UI and fix what needs fixing
- Wants specs split per PR, each with a brief explanation
- Wants the speaker's examples translated to concrete equivalents in this project
