# Restructure plan: rename handoff/ and tools/ phase names, then split src/ by .omm architecture layers

The user wanted to replace confusing phase-based names (handoff/phase2, tools/phase2_handoff.py, etc.) with clear names organised by pipeline and layer, so teammates can work through PRs. They agreed to two specs run in order: first move handoff/ records to docs/history/<topic>/ and rename tools/ scripts by function, then split the flat src/rfp_assistant/ package by the .omm architecture layers. Work was to start after PR #22 merged. PR #22, #23 and #24 were later reported merged.

## Decisions

- Do the work as two specs/PRs in order: records + tools renames first, then src/ split by layer — The renames are low risk and fix most teammate confusion; the src/ split is bigger because modules import each other
- Move handoff/ folders to docs/history/<topic>/, keeping the phase2 kit as docs/history/retrieval-selection-kit/ — handoff/ holds records, not code, so sorting it by layer would not help (rejected: Organising handoff/ by layer; deleting the phase2 kit)
- Name the src/ packages after the .omm overall-architecture layers — So the folder names match the architecture diagram
- Start the first spec only after PR #22 (team-VM deployment) is merged — PR #22 changes the same deployment files that the first spec moves into tools/infra/

## Facts

- src/rfp_assistant/ is one flat package of 32 modules, about 23k lines; service.py is 3,015 lines and evaluation.py is 2,495 (unverified)
- Phase names come from the delivery plan steps docs/plan/end-to-end/N-*.md and appear in handoff/, tools/, two test files and the plan docs (unverified)
- handoff/phase2 is a kit for an outside analyst called "Cloud"; phase3 is browser acceptance evidence for six-user workflows; phase4 is a synthetic release walkthrough on test data; postgresql-pgvector is the PostgreSQL migration record linked from README, runbook, release report and contracts doc (unverified)
- verification.json lists the handoff phase3 and phase4 READMEs (unverified)
- Proposed renames: phase2_handoff.py -> tools/export/retrieval_snapshot.py; check_large_quality.py -> tools/retrieval/fusion_gate.py; check_vector_search.py -> tools/retrieval/hnsw_recall.py; verification/phase4_walkthrough.py -> verification/release_walkthrough.py; start-postgresql.*, start-langfuse.ps1, postgresql-init.sql, bidmate.service, bidmate-cli.sh -> tools/infra/; test_phase2_handoff.py -> test_retrieval_snapshot.py; phase4_fixtures.py -> release_fixtures.py (unverified)
- Import cycles exist: service <-> evaluation, and ingestion -> ocr -> fidelity -> ingestion (unverified)
- The VM service unit runs rfp_assistant.api:app; the rfp-assistant command and bidmate-cli.sh run rfp_assistant.cli (unverified)
- .omm overall-architecture layers: HTTP API, service, retrieval engine, paid gateway, storage, offline pipelines (corpus intake/OCR/fidelity, index builds, evaluation and release, maintenance) (unverified)
- Do moves with git mv in a moves-only commit, then fix references in a separate commit, so git log --follow and blame keep working (unverified)
- PR #22 merged (round 12, 0 P2 remaining); PR #23 merged (round 3, 0 P2 remaining); PR #24 merged (round 2, 0 P2 remaining)

## Preferences

- Folder and file names should be clear and organised by pipeline and layer, not by phase numbers, so teammates can understand code they modify via PRs

## Open

- Proposed but not explicitly confirmed: keep api.py and cli.py at the package root so the codeit VM needs no redeploy
- Proposed but not explicitly confirmed: the src/ move does not break import loops; done condition is existing tests pass and web/openapi.json is unchanged; loops broken in later PRs
- Possible third task: renaming CLI phase flags (report --phase 2, check --phase 3) if teammates find them confusing
- Old decision/memory records keep old names; plan docs docs/plan/end-to-end/N-*.md are left unchanged
