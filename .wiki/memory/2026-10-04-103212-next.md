# BidMate RAG moved to PostgreSQL + pgvector with text-embedding-3-large at 1,536 dimensions (PR #11 merged)

The user first asked for a spec of everything the direct RAG path (parsing, chunking, vector DB, DB) still needs. They then asked whether moving to PostgreSQL + pgvector would improve search at the current scale, and requested an agent handover for the migration, including embedding dimension reduction to fit pgvector. They later switched the embedding model to text-embedding-3-large. PR #11 was merged, running BidMate on PostgreSQL with pgvector retrieval using validated 1,536-dimensional text-embedding-3-large embeddings, and PR #12 (round 3, no remaining P2) was also merged.

## Decisions

- Use PostgreSQL as the database with pgvector as the vector store, holding metadata, source revisions, chunks, embeddings and application records — Fits the current scale; the gain is unified storage, transactional updates and shared operation rather than automatically better retrieval accuracy (rejected: Current SQLite storage with in-process NumPy exact dense search)
- Switch embeddings to text-embedding-3-large, reduced below its native 3,072 dimensions to fit pgvector's 2,000-dimension HNSW/IVFFlat limit; the merged result uses 1,536 dimensions for both corpus and query embeddings (rejected: Previous small-model embeddings, which are kept for rollback rather than relabeled or resized into large-model ones)

## Facts

- Parsing, structural chunking, SQLite storage, keyword retrieval, dense indexing and reranking were already implemented before the migration (unverified)
- Before the migration, the local runtime served an older keyword index without the metadata snapshot the current retrieval policy requires, and had no recorded retrieval activation or registered dense index (unverified)
- The corpus has 100 document associations representing 98 distinct originals: 34 passed automatic fidelity comparison, 58 were flagged and 6 are unreviewed. These are extraction-check outcomes, not human approval (unverified)
- The two historically failed HWP documents have been recovered and still need independent review (unverified)
- The active index contains 18,983 searchable chunks (unverified)
- pgvector's standard `vector` type supports HNSW/IVFFlat indexing up to 2,000 dimensions; text-embedding-3-large's native output is 3,072 (unverified)
- Document and query vectors must use the same model and dimension policy; new vectors are reduced via the model's `dimensions` parameter (unverified)
- PostgreSQL alone does not remove the application's single-worker gateway restriction (unverified)
- The migration had to preserve application records, evidence identities and the spending ledger's atomic admission and settlement (billing guarantees)
- PR #11 merged: BidMate runs on PostgreSQL with pgvector-backed retrieval using validated 1,536-dimensional text-embedding-3-large corpus and query embeddings
- PR #12 merged: round 3, no remaining P2 issues

## Preferences

- When asked for a spec: write it immediately, do not ask clarifying questions, choose the completion criteria yourself, and include every task without trimming any
- Wants work handed to other agents through a written handover document (인계서)

## Open

- Whether pgvector improves retrieval speed is unmeasured. The proposed benchmark compares NumPy exact vs pgvector exact vs pgvector HNSW on the same embeddings, questions and scopes, measuring p50/p95 at 6 concurrent requests, top-20 recall vs exact, required-source coverage and full-answer latency
- Add HNSW only if measured latency warrants it, checking scoped recall under filtering
- Proposed to keep Kiwi BM25, exact requirement-code lookup and RRF fusion rather than PostgreSQL ts_rank; not explicitly confirmed
- Pilot failures remain: incomplete obligations, one-sided comparison citations, unnecessary refusals and incorrect conflict handling, some occurring despite complete packed support
- Human fidelity review of the 58 flagged and 6 unreviewed documents, plus the two recovered HWP files
- Single-worker gateway restriction remains
