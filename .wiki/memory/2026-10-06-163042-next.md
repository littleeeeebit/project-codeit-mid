# GCP deployment plan for team access: SSH-tunnel-only VM, members code locally, repo to go public

The user asked how to deploy project-codeit-mid to GCP so teammates can use the frontend and work on code, with no separate login session beyond their existing SSH keys. The assistant proposed a single Compute Engine VM exposing only port 22, with the app on 127.0.0.1:8501 reached by SSH port forwarding. The user chose to check the active run before sizing the VM, to use code-work option 2, which requires a README update and making the repository public, and to migrate the live DB dump plus the original documents. The conversation ended with the assistant splitting the work into two branch specs, GCP deployment and public repo/README, with several publishing questions still waiting on the user.

## Decisions

- Decide VM size only after checking which serving run is active on the host; switch to a GPU VM only if that run uses a local model
- Code work option 2: members work on their own machines, and the VM only serves the shared instance, reached through an SSH tunnel (rejected: Per-member Linux accounts on the VM with their own clones, edited via VS Code Remote-SSH)
- Update README.md and switch the repository to public as part of option 2
- Migrate data as a live DB dump plus the original documents
- Access only via SSH key with a port forward, no separate login session — Members already authenticate with their own SSH keys; the user required no additional login (rejected: IAP TCP forwarding and OS Login (need a Google sign-in), Cloud Run, binding 0.0.0.0 or a public load balancer)

## Facts

- App has no login; network reach is the only access control. Binding to 0.0.0.0 would expose the shared budget and admin pages (unverified)
- App binds to 127.0.0.1:8501; access is `ssh -L 8501:127.0.0.1:8501 <member>@<vm-ip>`, then http://localhost:8501 (unverified)
- The API serves built frontend screens from `web/out` plus the `/api/` routes on one port; needs `npm run build`, then uvicorn (unverified)
- The typed 이름 field records who did what (unverified)
- Only one server process may own the paid-gateway lock; the runbook says to run a single worker; the budget DB must never be copied into a second ledger that can spend on its own (unverified)
- The app needs a long-lived single process and PostgreSQL 18.6 with pgvector (unverified)
- PostgreSQL is started via Docker Compose through a Windows PowerShell script; Linux needs Docker Engine plus pwsh or a shell equivalent (unverified)
- Local embedding/reranker models refuse to run on CPU (unverified)
- Serving uses hybrid run `H-0fffb2a6ec` with OpenAI text-embedding-3-large vectors and no local reranker, so a CPU VM suffices for serving; OCR and local-model comparisons need a GPU (unverified)
- Live database is `bidmate_app`; it and the original documents are not in git. Restore requires a verified dump and `restore-check`, which leaves paid admission off until reconciled (unverified)
- The runbook asks that the chosen host and who can reach it be recorded in the phase-3 report (unverified)
- Repository is currently private; a quick history scan found no original PDF/HWP/CSV, no .env, and no real API keys, only test placeholders (unverified)
- Members' local setup: fake provider against their own empty PostgreSQL in Docker, no budget or API key (unverified)
- After the VM restore is verified, the owner's local server is stopped so the VM is the only live server (unverified)

## Preferences

- No separate login session: authentication only through each member's existing SSH key
- Members must be able to run the frontend and also do code work
