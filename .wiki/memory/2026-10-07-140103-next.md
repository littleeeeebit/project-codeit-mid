# Restore BidMate login via JupyterHub OAuth and serve publicly at http://35.255.64.243:8501

The user asked to restore the previously removed login so teammates can use the same ID/password as the JupyterHub at http://35.255.64.243:8000/. They also asked to deploy the frontend as a web page that teammates open in a browser without running commands, and asked how the API would be handled. The user chose JupyterHub OAuth registration, the public address on port 8501, a six-member allowlist in server.env, and an account-bound OpenAI key with all pages open to members. A spec followed. PR #25 and PR #26 were then merged with 0 remaining P2.

## Decisions

- Authenticate BidMate users by registering BidMate as a JupyterHub OAuth app (a `bidmate` service in the hub's jupyterhub_config.py) — IDs/passwords match the hub's by construction and stay in sync on password changes, instead of copying passwords that would drift (rejected: Keeping BidMate's own copy of the hub passwords)
- Serve BidMate publicly at http://35.255.64.243:8501 by binding uvicorn to 0.0.0.0:8501 on the already-open port, only after login is enforced — Teammates open it in a browser without commands; the shared firewall already opens 8501, so no firewall change is needed (rejected: Loopback-only binding reached through an SSH tunnel)
- Restrict access to the six listed members via an allowlist in server.env
- Tie the OpenAI key to the logged-in account (still memory-only); keep all pages, including admin, open to every member (rejected: Keying the OpenAI key to a per-browser cookie session)
- Reverse the earlier owner decision to remove login (reaffirmed for phase 3 and in the move to codeit) — Needed so teammates can log in to the web deployment
- Every /api route takes identity from the login session and returns 401 without a session, replacing trust in the X-Member header — X-Member only carries a name the visitor typed; it verifies no one (rejected: Free-text name field / X-Member header as identity)

## Facts

- Port 8000 on VM `codeit` is the team's JupyterHub (version 6.0.1), running alongside BidMate; reachable internally at 127.0.0.1:8000 (unverified)
- The hub login page is a plain username/password form with no sign-up link; it may use the VM's Linux accounts spai1302…spai1322, but the hub config was not seen (unverified)
- One uvicorn process serves both the built screens (web/out) and all /api/* routes on one port; the browser calls relative /api/... paths, so no separate API host, CORS, or public RFP_API_URL is needed (RFP_API_URL matters only for `npm run dev`) (unverified)
- Before this work, uvicorn listened only on 127.0.0.1:8501, reached via SSH tunnel; the runbook forbade --host 0.0.0.0 because there was no login (unverified)
- Plain HTTP sends passwords in the clear, as the hub on :8000 already does; these may also be members' Linux passwords (unverified)
- 35.255.64.243 is ephemeral and changes if `codeit` is stopped and started; the OAuth return address must then be updated in both the hub registration and server.env (unverified)
- PR #25 merged after round 4 with 0 remaining P2
- PR #26 merged after round 2 with 0 remaining P2

## Preferences

- Teammates must reach the deployed frontend through the web, not by running commands to start a local frontend
- Login IDs and passwords should match the JupyterHub accounts at :8000 so teammates log in easily
- The user decides when the shared hub config is edited and restarted, and confirms before the public 0.0.0.0 bind
