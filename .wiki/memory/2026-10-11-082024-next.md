# Separate local A/B review app for pipeline stages, plus a shared Langfuse on codeit over SSH tunnels (PRs #36–#38 merged)

The user wanted a separate local frontend so a person can compare pipeline variants (retriever, chunking, generation, OCR) side by side and send decisions back to a coding agent, because `notebooks/before_after.ipynb` is not intuitive. They also wanted the local Langfuse moved onto the team server so teammates' traces can be viewed right away. The work was split into three specs: review app PR 1 (retriever/chunking), review app PR 2 (generation/OCR, with trace links), and a shared Langfuse on `codeit`. PRs #36, #37 and #38 were merged. #37 still has one P2 remaining.

## Decisions

- Build the review frontend as a separate app, independent of the existing web app, run locally with a .cmd launcher and a Mac launcher — A/B comparison between pipelines is hard today and the ipynb is not intuitive. A person needs an interface that is easy to review. (rejected: Relying on notebooks/before_after.ipynb or the existing 실험 비교 screen inside the main app's 검증 area)
- Candidates are git refs: a baseline commit plus N branches, commits or the working tree
- Execution is done by a CLI runner on the same frozen inputs. The app only views results and records decisions
- A decision is output as a decision file plus a copy-ready prompt for the coding agent
- Stack: a separate Next.js app in `review/`, static export served by a small Python server
- The Mac launcher opens the viewer, runs CPU/API stages, and shows GPU stages from imported results — Local embedding/reranker models refuse to run without CUDA, PaddleOCR-VL needs a local GPU, and retrieval needs PostgreSQL/pgvector (rejected: A full-parity Mac launcher)
- Split the review app into two PRs (retriever/chunking first, then generation/OCR from main after the first is merged), with the shared Langfuse as a separate third spec — The second PR builds on the first PR's runner, result and decision contract
- Generation/OCR review shows a link from each generated answer to its trace when tracing is configured
- Host the shared Langfuse on `codeit`, bound to 127.0.0.1 and reached through SSH tunnels — All six members already have SSH keys and sudo on codeit, so no public port is needed (rejected: Opening a public port)
- Use only free disk space on codeit, with no new disk (rejected: Enlarging the boot disk or adding a data disk)
- Use one shared Langfuse project. The team server and every member's local runs send to it, tagged by member, environment and git ref
- Each member gets their own Langfuse account. Sign-up is turned off after the six are in
- Migrate existing local traces to the shared server

## Facts

- notebooks/before_after.ipynb runs a pinned commit A and a working-tree snapshot B in separate processes on the same inputs. It covers parser, chunker, BM25 search, evidence assembly, prompt and answer validation, and writes JSON/HTML reports under .runtime/notebook-comparisons/. It handles exactly two versions (unverified)
- `compare --matrix` and the 실험 비교 screen in the main web app's 검증 area show aggregate tables for chunking, embedding and reranker variants. They do not handle agent-built branch candidates and cannot send decisions back (unverified)
- No OCR comparison view existed before this work. The latest OCR rework reads images from the HWP file itself and uses gpt-5-mini to re-read flagged local reads (unverified)
- The local Langfuse is a Docker Compose project `bidmate-langfuse` (Postgres, ClickHouse, Redis, MinIO), started by tools/infra/start-langfuse.ps1. It traces only /api/ask and drafting runs, not embeddings, ingestion, OCR or evaluation (unverified)
- Tracing sends full text, with secrets masked by a single function at the client exit. Tracing never affects answers or the ledger (unverified)
- The live team server on codeit runs with Langfuse tracing turned off. Turning it on needs a `bidmate` restart, which signs everyone out and drops their entered API keys (unverified)
- codeit is a g2-standard-4 VM (4 vCPU, 16 GB RAM) shared with JupyterHub and BidMate. Its 50 GB boot disk had about 1.2 GB free after the 2026-10-09 cleanup. Room must be left for the server's web/ rebuild that the in-app update button depends on (unverified)
- The planned trace migration restores the local stack's databases into the server stack on the same Langfuse version rather than replaying traces through the API. This also carries over the existing login and project (unverified)
- The planned setup keeps new tracing API keys on the VM in a root-only file. Members copy them into their own git-ignored .env (unverified)
- Local runs are tagged with the member name from BIDMATE_LOCAL_MEMBER. Server traces carry the signed-in account (unverified)
- A local Langfuse already runs on 127.0.0.1:3001 on the user's PC. Two Langfuse UIs on the same loopback address break each other's sign-in, so the tunnel address must differ (unverified)
- PR #36 merged (round 5, 0 P2 remaining). PR #37 merged (round 6, 1 P2 remaining). PR #38 merged (round 3, 0 P2 remaining)

## Preferences

- The review frontend must be separate from the existing frontend and run locally, with a .cmd launcher and a Mac-specific launcher
- Intended workflow: a coding agent implements B or several candidates, the human runs the frontend to see results at a glance, decides there, the decision goes to the coding agent, and the agent proceeds on it
- For risky steps (disk space, closing sign-up, enabling server tracing), the session should stop and ask rather than guess or touch teammates' files
