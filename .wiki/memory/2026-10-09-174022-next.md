# Answers move to gpt-5-mini, default embedding becomes BGE-m3-ko after an 11-candidate answer comparison; PRs #29–#31 merged

The user said the project API key does not serve text-embedding-3-large (429), so answers must use gpt-5-mini. The user asked which embedding works best with gpt-5-mini answering, from the earlier candidate list minus Gemini and text-embedding-3-large. A spec was written to remove gpt-6-luna from answering and to run all 11 hybrid rows through answer evaluation. PR #29 then made gpt-5-mini the answer default and dragonkue/BGE-m3-ko the default embedding. PRs #29, #30 and #31 were all merged with no P2 findings left.

## Decisions

- Use gpt-5-mini as the answer (chat) model in this project. Update records naming gpt-6-luna as the answer model, and remove gpt-6-luna from answering, including as a fallback. — gpt-6-luna applies only to the user's personal end-to-end setup. In this project the provided API reaches gpt-5-mini, and gpt-6-luna becomes a fallback. (rejected: Keeping gpt-6-luna as the answer model or as an answering fallback)
- Embedding candidates are the earlier list minus Gemini and text-embedding-3-large: text-embedding-3-small plus the ten local models (11 total). — The provided API does not serve text-embedding-3-large (429). (rejected: Gemini and text-embedding-3-large)
- Measure all 11 hybrid rows through answer evaluation, not through retrieval metrics alone. (rejected: The retrieval-only embedding comparison table)
- Keep gpt-6-luna for the other LLM roles (dataset drafting, judges, AI review), run on the user's personal key.
- Use the user's personal API key for intermediate evaluation, iterative improvement, and the final comparison run. (rejected: The team key)
- Treat text-embedding-3-small as servable on the team key. — Another team member confirmed it works.
- Run the answer and embedding change as one spec rather than two branches. — The measurement depends on gpt-5-mini answering in evaluation runs, so separate branches would wait on each other or measure with the wrong model. (rejected: Two separate specs or branches)
- Stash the uncommitted frozen-corpus-validation work, including untracked files, before opening the next task branch. — The work is unfinished. A plain stash would leave the untracked trial scripts behind, and they would land on the next branch. (rejected: Committing the changes, or a plain `git stash` without -u)
- To finish PR #29, rewrite only the doc passages that still state current defaults. Leave proposal-era pages that mention gpt-4o-mini as they are. — Proposal-era pages read as history, not as current defaults. (rejected: Rewriting the historical pages too)
- Leave PR #29's branch history alone, including the commit that is cancelled by its own revert. (rejected: Rewriting branch history)
- Review PR #29 until clean, then merge.

## Facts

- Default answer model is gpt-5-mini. Default embedding is dragonkue/BGE-m3-ko at 1,024 dimensions, and its measured hybrid row H-5b2565f606 is active on both hosts; the owner chose it after the comparison (unverified)
- Paid comparison run E-9b785d7cd167 answered the same 35 development questions for 12 rows: the 11 hybrid embedding rows plus keyword-only K1. It cost $1.930667 against a $3 ceiling (unverified)
- The comparison baseline is keyword-only K1, not text-embedding-3-large, because keyword-only is what the team key gets while 3-large returns 429 (unverified)
- In hybrid mode, `keyword_first` fusion keeps the first six BM25 results fixed, so embeddings only change the evidence after them. The retrieval-only table gave every model the same hybrid nDCG@5 of 0.9405 (unverified)
- Dense-only nDCG: KURE-v1 scored 0.7401, the best local model, against 0.6547 for text-embedding-3-large. The app does not serve dense-only retrieval (unverified)
- When a key has no embedding access, retrieval silently falls back to keyword-only search, recorded as `hybrid->kiwi_bm25:query_vector_unavailable`; answers still arrive without the dense channel (unverified)
- The team key reaches only gpt-5-mini and gpt-5-nano among generation models, per the runbook and settings note (unverified)
- Dataset drafting used to refuse to run unless the configured answer model was gpt-6-luna, so the drafting model had to be separated from the answer model. Judges and AI review name gpt-6-luna on their own (unverified)
- Any config.json, local or on `codeit`, that sets `generation_model: gpt-6-luna` stops loading once gpt-6-luna is no longer allowed for answering (unverified)
- jina-embeddings-v3 is non-commercial and embeddinggemma is under Gemma terms; both are labelled research-only (unverified)
- Paid runs are charged to the shared $20 ledger and must stop for owner approval of the estimate before spending (unverified)
- Picking and activating the winning embedding is the owner's decision on the 실험 비교 screen (unverified)
- The frozen-corpus-validation stash holds the following: the preflight no longer chunks by default (only with `--preview-chunking`), it checks that `raw_element_reference` stays inside the package, and it adds a `parsing_input` report section. It also holds the untracked scripts frozen_corpus_trial.py and frozen_mapping_trial.py (unverified)

## Preferences

- Use the user's personal API key for intermediate evaluation and recursive improvement during implementation
- gpt-6-luna as answer model is only for the user's personal end-to-end setup, never as this project's answer default
- Choosing and activating the winning embedding stays the owner's decision
