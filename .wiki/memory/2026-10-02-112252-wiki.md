# How the project's HWP parser pipeline works (pyhwp XML walker, Hancom-printout fallback, OCR, fidelity check)

The user asked, in Korean, how the 'PWH' (taken to mean HWP) parser is structured, both in the docs and in the actual code pipeline, explained simply. The assistant described a chain wired into `ingest`: pyhwp converts HWP to XML, the project's own walker cuts it into labelled elements, a Hancom Viewer PDF printout serves as a fallback, OCR adds text from images, and `fidelity run` checks the result against a Hancom printout. It reported the Phase 2 baseline counts and the remaining open items. The answer was unverified and the user did not reply.

## Facts

- 'PWH' in the question was interpreted as HWP; 96 of the 100 RFP originals are HWP (unverified)
- HWP parsing is wired into the `ingest` pipeline; the HWP walker is at version `hwp-xml-walker-3` (unverified)
- Conversion uses pyhwp: `hwp5proc xml --output … original.hwp`, run as a separate process with a timeout; output is validated, so empty or broken XML counts as failure even when the exit code is success (unverified)
- `hwp5txt` is deliberately not used because it lost table contents in sample checks (unverified)
- The walker emits elements in document order typed `paragraph`, `heading`, `toc`, and `table`. Headings are detected from numbering patterns such as "1.", "가.", "Ⅰ", and each element records its section (unverified)
- Tables keep row, column and merged spans per cell. Nested tables become separate elements linked to their parent cell so that no text is counted twice (unverified)
- Text boxes and picture captions are kept, and headers and footers are dropped. One-row title-box tables (e.g. "Ⅰ | 사업 안내") are treated as headings (unverified)
- Equations are empty in pyhwp XML, so the walker reads the equation script from the HWP binary and converts it to symbols such as ×, ≤, √ (unverified)
- Element IDs combine the extraction revision with a structural position (e.g. `s0/p12/t0`), and the consultant screen uses that position to locate citations (unverified)
- If pyhwp fails and a Hancom Viewer printout exists, that PDF's text layer is parsed and the elements are tagged `hwp_print`. If neither works, the source is quarantined with reason codes such as `hwp_xml_malformed` or `hwp_converter_decode_error` (unverified)
- PaddleOCR-VL reads image regions on the printout, with a Gemini fallback capped at $0.50. Its text becomes `image_text` elements that are chunked and cited separately as OCR (unverified)
- `fidelity run` prints each HWP to PDF via Hancom Viewer and compares lines in both directions; runs of 3+ digits must match exactly. Verdicts are `auto_verified` or `auto_flagged`, together with the differing locations (unverified)
- The chunker splits tables into row groups and keeps the short title lines just above a table with it (unverified)
- HWPX copies are refused; the code says a parser for them will be added only when a real file needs one (unverified)
- Phase 2 baseline: all 98 unique originals parsed (after merging two byte-identical duplicate pairs) and none were quarantined (unverified)
- AFSIS Cambodia and MILE cannot be converted by pyhwp and came through the Hancom-printout fallback (unverified)
- Phase 2 baseline fidelity: 92 verdicts, 34 `auto_verified` and 58 `auto_flagged` (unverified)
