# Maintenance run hung in ingest: decided per-file child-process parse with timeout, instant cancel, per-file progress (PR #44 merged)

The user reported that a maintenance run started Oct 10 23:31 was still shown as running hours later. They asked whether it was a display error, how to shorten the time, and for a cancel feature. The assistant reported, unverified, that the run was really stuck: one thread was spinning at 100% CPU on a single HWP original during ingest. The user chose four design decisions, the assistant turned them into one task spec, and PR #44 was merged (round 4, 0 remaining P2).

## Decisions

- Fix the hang at the root cause and add a per-file time limit, running each parse in a child process
- A file that times out keeps its previous extraction, is flagged, and the run continues
- Cancel button stops the run at once, kills any running parse, and the run ends with status `cancelled`
- The maintenance page shows per-file progress and elapsed time
- Ship the hang fix, time limit, cancel and progress as one spec rather than separate tasks — A child-process parse is what makes a hard time limit and an instant cancel possible. Split apart, the cancel button still could not stop the current kind of hang. (rejected: Splitting the four pieces into separate tasks)

## Facts

- The long-running maintenance was a real hang, not a display error. Run started Oct 10 23:31 UTC. Backup took about 12 min and the restore check about 7.5 min. Ingest re-parsed and saved 59 of 98 originals in 94 s, then wrote nothing after 23:52:24 (unverified)
- One server thread sat at 100% CPU for over 7 h while the other 20 threads were idle (unverified)
- Likely culprit, inferred from DB document order and not from a stack dump: `케빈랩 주식회사_평택시 강소형 스마트시티 AI 기반의 영상감시 시스템 .hwp`, which parsed in 3.46 s on Oct 5 (unverified)
- All originals were re-parsed because #34 (unreadable-by-pyhwp HWP routed through `HwpHwpxLoader`) and #35 (HWP image text from embedded pictures) changed the parser fingerprint, the version tag that triggers re-parsing. Both are suspects for the hang (unverified)
- A healthy maintenance run takes about 25 min, of which about 20 min is backup plus restore check (unverified)
- Before the fix, the code checked for a stop request only between steps, so a thread stuck in a parse could not be cancelled (unverified)
- The status page shows a run whose thread is gone as `interrupted` (unverified)
- Restarting `bidmate` (`sudo systemctl restart bidmate`) signs everyone out and drops the API keys members entered. Shutdown may wait out systemd's stop timeout because of the stuck thread (unverified)
- Spec behavior: cancel kills the child parse immediately during ingest. Backup, restore check, embedding and the regression table stop at the next step boundary, and the page shows 취소 중 until then (unverified)
- Spec behavior: a run with timed-out files ends in the existing `unverified` status, with a reason naming those files. No new status was added (unverified)

## Open

- The user did not explicitly confirm two spec choices that went beyond their picks: step-boundary cancel (취소 중) outside ingest, and reusing `unverified` status for runs with timed-out files. PR #44 was later merged.
- The run stuck on the VM still needs a `bidmate` restart at a time the user chooses, because a restart signs everyone out.
- The root cause was not confirmed. The suggestion was to run `py-spy dump` on the live process before restarting to get the exact stuck line.
- Backup and restore check could be made faster if normal runs should be shorter. This was not pursued.
