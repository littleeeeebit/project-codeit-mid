`submit_answer` validates, checks the conversation chain, and inserts the `requests` row as `queued` with `request_json` (question, scope, mode, as_of, previous_request_id, capabilities) and `config_hash`, all in one mutex transaction that also takes a runner slot. It returns {request_id, generation_id, target = sha256(scope, question, mode, as_of, previous)}. If enqueueing fails, `_fail_unscheduled` marks the row `failed` and frees the slot. Nothing has been reserved at this point.
