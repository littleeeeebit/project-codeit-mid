`submit_answer` (service.py:976) runs `_validate_request` (mode, question length, 1–2 distinct documents or none for corpus, exactly 2 for compare, frozen verifier run still valid). It then runs `_conversation`, which refuses a follow-up whose earlier turns belong to another member, are unfinished, or used a different scope. Free modes are created as `running` and executed inline on the HTTP thread. Paid modes go through `_create` with status `queued`: one immediate transaction looks up (member_id, idempotency_key), returns the prior row when the input hash matches (a double click or rerun never starts a second call), refuses a reused key with different input, takes an executor slot, and inserts the request with its config snapshot and request_json. If `runner.submit` then fails, the slot is freed and the row is marked failed with no paid call. Verifier generation (`generate_from_run`) uses the same path with idempotency key `vgen-<run_id>` and a frozen run.
