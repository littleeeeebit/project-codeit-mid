`submit_answer` runs `_validate_request`. It checks the mode, question length (1..`question_max_characters` for paid modes), duplicate documents, scope size per mode (corpus takes zero documents, compare exactly two, others one or two), key length and `_frozen_run_for`, so a mismatched verifier run is refused before anything is queued. `_create` computes `input_hash` (normalized question, scope, mode, as_of, config, run) and a config snapshot (index, serving run, prompt version, model, rate version, settings fingerprint). In one mutex transaction it either returns the prior row for the same `(member_id, idempotency_key)` (a different input raises 'same key reused') or inserts the request. Free modes insert `running` and execute inline on the HTTP thread. Paid modes insert `queued` after acquiring an admission slot (a full queue → 'too many requests, no paid call') and then `runner.submit(request_id)`. If submit fails, the slot is released and the request is marked `failed` by `_fail_unscheduled`.
