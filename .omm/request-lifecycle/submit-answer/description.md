`_validate_request` checks mode, question length (paid modes need 1..`question_max_characters`), scope cardinality per mode (corpus takes none, compare exactly two), no duplicates, and the frozen verifier run if any. `_conversation` is checked before anything is queued, so a bad follow-up is refused up front. Free modes: `_create(status='running')` then `_execute` on the request thread. Paid modes: `_create(status='queued', before_insert=admit)`. Inside the idempotency transaction, a new key must win a runner slot (`try_admit`, refused while the update fence is up or the queue is full). An existing `(member_id, idempotency_key)` returns the prior request if `input_hash` matches and errors otherwise. A submit failure releases the slot and marks the row `failed` (`_fail_unscheduled`).
