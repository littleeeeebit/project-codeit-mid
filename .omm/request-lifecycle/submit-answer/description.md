`service.ask` creates a fresh `generation_id`, used both as the generation ID and as the idempotency key, and calls `submit_answer`. That runs `_validate_request`: mode, 1–`question_max_characters` characters for paid modes, no duplicate refs, corpus only with an empty scope, compare with exactly two, and a frozen-run match. It then runs `_conversation`: every earlier turn must belong to this member, be finished and have the same scope, and up to 6 turns are rebuilt with the previous answer's cited evidence carried (≤ 8 units). `_create` inserts the `requests` row under `(member_id, idempotency_key)` with the input hash, a config-snapshot hash and the request snapshot, in one `immediate` transaction. A repeated key with the same input returns the existing request; with a different input it is refused. For paid modes, `runner.try_admit` runs inside that transaction before the insert, and `runner.submit(request_id)` follows. A submit failure frees the slot and marks the row failed (`_fail_unscheduled`).
