`service.ask` generates a fresh `generation_id` (also used as the idempotency key) and calls `submit_answer`. `_validate_request` checks the mode, question length (1..`question_max_characters` for paid modes), scope cardinality per mode, and any frozen verifier run. `_conversation` validates the chain of previous turns (same member, terminal, same scope) before anything is queued. `_create` checks for an existing `(member_id, idempotency_key)`: the same input hash returns the prior request, and a different hash raises 'same key reused with different input'. Otherwise it admits a runner slot inside the transaction and inserts a `requests` row with `status`, `input_hash`, `config_hash`, `scope_json`, `request_json` (the snapshot used to rebuild the request) and `trace_json.config`. If `runner.submit` fails, the slot is released and the row is marked `failed`.
