`submit_answer` → `_validate_request` checks mode, question length, one or two distinct documents (exactly two for compare, none for corpus) and a known frozen run. `_conversation` validates the conversation chain before anything is queued: same member, terminal status, same scope, at most 6 turns. Free modes call `_create(status="running")` and execute inline. Paid modes call `_create(status="queued", before_insert=admit)`, which inside one immediate transaction returns any prior row with the same (member_id, idempotency_key), refuses a reused key with a different `input_hash`, calls `runner.try_admit()` (update fence plus semaphore; a full queue raises ServiceError before any paid work), and inserts the `requests` row with `request_json` and the config snapshot. A failed `runner.submit` releases the slot and marks the row failed (`_fail_unscheduled`).
