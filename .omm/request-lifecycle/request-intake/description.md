`service.ask` creates a fresh `generation_id`, which also serves as the idempotency key, and calls `submit_answer`. Validation (`_validate_request`) checks mode, question length, duplicate scope, mode/scope arity, and frozen-run consistency. `_conversation` validates the conversation chain. `_create` computes the `input_hash` (and the previous turn, when present) and, in one mutex transaction, either returns the prior row for the same `(member_id, idempotency_key)` (and refuses a different input under the same key) or admits a runner slot and inserts `requests(status='queued', request_json, trace_json.config)`. `runner.submit(request_id)` follows; if scheduling fails, the slot is released and the row is marked `failed` with nothing paid. The response is `{request_id, generation_id, target: target_key(scope, question, mode, as_of, previous)}`.
