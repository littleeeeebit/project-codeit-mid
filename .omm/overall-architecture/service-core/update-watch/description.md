`update.UpdateWatch` is configured by `BIDMATE_UPDATE_REQUEST` and `BIDMATE_UPDATE_STATE_DIR`. It records `build_head()` at startup, polls GitHub's `/repos/littleeeeebit/project-codeit-mid/commits/main` and the compare endpoint every 300 s unauthenticated, and reads the root updater's `result.json` and `update.log`. `request_update` raises `accepting` under `_runner_lock` and checks `open_paid_work`: admitted slots, queued or running rows, live jobs, then open or unknown ledger attempts, in that order so nothing is missed. It refuses if anything is open; otherwise it writes the marker file atomically and audits `request_update`. The root `bidmate-update.path` and `.service` units run `tools/infra/update.sh`, which fast-forwards, rebuilds, restarts, health-checks and rolls back. That script is outside this analysis; it is described from the docstring. `fenced()` stays true while the marker exists or the result says running.
